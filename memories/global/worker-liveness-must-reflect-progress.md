For any long-lived worker/daemon that ticks a work loop, two failure patterns recur and must be designed against:

**1. A liveness/health signal must reflect real forward PROGRESS, not just "the process is alive."**
A blind heartbeat written on its own interval keeps a "live" badge green even when the loop does zero work. The honest signal is a `last_progress_at` stamped at genuine units of forward work (a job finishing, a chunk persisting, a queue item processed), with liveness = `live` only when heartbeat AND progress are both fresh; `stalled` = process alive but no progress past a threshold. Crucial subtlety: a legitimately long single unit of work (e.g. a 52-min batch) must keep stamping progress so it reads `busy/live`, not `stalled` — so stamp at a fine grain (per chunk/item), and set the stall threshold above the longest legitimate *inline* awaited unit (e.g. one LLM call bounded by the SDK's HTTP timeout). Update EVERY consumer of the liveness signal (badge AND any health-check/alert surface), or one still reports healthy while frozen.

**2. A single-flight loop with no watchdog + an unbounded awaited task = a silent total freeze.**
If `tick()` does `await someTask()` behind a `ticking` flag, and `someTask` hangs forever (a network call with no timeout, a dead remote machine), the flag stays set and every future tick is skipped — the whole worker freezes while the heartbeat keeps beating. Defenses, layered: (a) bound every external await with a timeout (wall-clock, decoupled from any virtual/pacing clock, cleared+unref'd); (b) make non-essential dispatches fire-and-forget instead of awaited (mirror how cron/independent tasks already run); (c) a self-heal watchdog that releases ONLY the single-flight lock when the loop makes no progress for the threshold — never cancel/force-finish the hung task (that orphans concurrent work); guard the released lock with a per-tick token so a late-settling orphan can't clobber its successor, plus an in-process id-set / status re-check so a resumed orphan can't double-execute.

Real incident (your-other-project, 2026-07-06): a hung zone-burst retry froze the your-data-product worker for 70 min while "Worker live" stayed green and an approved batch sat unexecuted. Fix shipped + proven live under the exact repeat condition. See project memory `[[session-2026-07-06-worker-antifreeze-shipped]]`.

**2b. Writing the liveness signal must never be able to KILL the worker, and no timer callback may throw.**
The beat is a signal, not work: if its write fails (a lock held by another writer, a full disk), skip the beat and log — a stale timestamp is the honest degraded signal every consumer already reads. An uncaught throw inside a `setInterval`/`setTimeout` body ends the process outright, and under a supervisor (Fly, systemd, k8s) that becomes a restart of everything the box was doing. So: guard EVERY timer body, give each arm its own catch and message (a failed beat must not skip the same callback's watchdog arm, or the two failures compound into a worker that is silent AND stuck), and guard the synchronous call into async work too — a function that throws before returning its promise is invisible to `.catch` and leaves the single-flight lock held forever. Prefer these local catches to a global `uncaughtException` handler, which hides corrupted state.
Corollary about contention: **fixing a lock-loss crash on one side can move the crash to the other side.** After making a batch job take write reservations up front, enumerate who else writes that resource and confirm each survives being refused. Incident (your-other-project, 2026-08-11): a migration switched to `BEGIN IMMEDIATE` to stop losing the WAL race, whereupon the worker's unguarded heartbeat write took the `SQLITE_BUSY` instead and the machine restarted mid-migration — `[[session-2026-08-11-migration-crashes-two-fixes]]`.

**3. Claude Code subagents are such workers — their own "wait for my background task's notification" is not a reliable resume signal.**
Observed 2026-07-21 (your-project, TO-DO 27): an implementer subagent launched its e2e suite with `run_in_background` from *inside its own context*, ended its turn "waiting for the notification", and was never re-invoked when the suite finished — the branch sat idle with all test processes exited until the controller messaged it (SendMessage resumes an idle agent). Defenses when orchestrating subagents:
(a) dispatch prompts must require **foreground execution in SHORT, transcript-visible calls**: plain Bash with explicit timeout (≤600s per call, long suites split into sequential chunks), never `run_in_background` inside the subagent, all *waiting* done as repeated bounded calls (≤~8 min each, a one-line status note between polls) rather than one long silent poll call, and "never end your turn while anything you started is unfinished — end only with your final report". One long silent call is indistinguishable from a hang from outside, and it also blocks message delivery: a SendMessage nudge queues until the call returns, so the agent looks unreachable precisely when it is busiest;
(b) controller-side **staleness watchdog, armed AT DISPATCH TIME and persistent**: a Monitor loop that emits one event per stall (≥ ~20 min with no file writes in the agent's work dirs AND no worker processes — codex exec/vitest/build — alive), then sleeps ~25 min before re-checking so one stall yields one nudge; silence must wake the controller, because from outside it looks identical to "still running". **The watchdog is itself a control that must be able to fire, and three implementation traps each silently make it unfirable — measured 2026-08-18, all three in one session:** a `pgrep -f` pattern matches the probe's OWN argv (bracket-escape it: `exe[c]`, or filter `$$`); the pattern matches SIBLING sessions' identical tooling in other worktrees, so their work reads as your agent's liveness (scope it to `-C <this worktree>`); and the watched path set omits where the agent actually writes — a subagent works in the SCRATCHPAD, not only the repo, so a live micro-review plus mutant build read as 20 minutes of silence and produced a FALSE STALL on an agent that was fine. Before arming, run the probe twice to prove BOTH branches reachable (once at the real threshold, once at a threshold that must flip it), and reproduce any alarm against the agent's real workspace before killing anything — [[absence-needs-a-probe-that-could-see-presence]] applies to your own instrument. A fourth trap, measured 2026-08-19: an agent inside one long foreground poll call shows NO transcript writes and NO worker binaries — its only live process between checks is `sleep`, which a `pgrep` for codex/vitest/gh misses — and an undelivered nudge is therefore evidence of a long call in flight, NOT proof of death; inspect the agent task's process tree (a shell + sleep under its session counts as alive) before declaring it dead. A long `sleep` in a Monitor loop can also die on SIGURG (exit 144) without ever running a check: `trap '' URG` and sleep in short chunks;
(c) on each stall event the controller **auto-revives without waiting for the human**: a SendMessage nudge queues if the agent is mid-turn and resumes it if idle, so nudging on suspicion is cheap and safe — this is the user's standing directive (2026-08-16: "whenever something is stalled can we revive it"). A wrong TaskStop is also recoverable: SendMessage to a killed agent RESUMES it with its context intact (measured 2026-08-19: a merge shepherd killed mid-CI-poll resumed cleanly, still holding its resolved-conflict state) — so after a mistaken kill, resume the same agent rather than redispatching, and fold the short-call waiting mandate into the revival message so the false stall cannot recur.
Second observed instance (your-other-project, 2026-08-16): the agent's backgrounded vitest finished in 57s but the completion notification took ~70 min to arrive; the agent sat idle-not-wedged the whole time and the nudge both resumed it and delivered the lost signal. Lost/late task notifications are a real mode even for harness-tracked work — treat "waiting on a notification" as stalled once the watched process is provably gone. Third mode, same day: a background task launched with a finite timeout whose PROCESS outlives the tracker's expiry keeps running but can no longer wake anyone on completion — for an indefinite wait (a human-feedback poll), use a persistent/no-timeout watcher, never a default-timeout task.
