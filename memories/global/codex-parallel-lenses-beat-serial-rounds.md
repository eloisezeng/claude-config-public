Run each convergence stage as **parallel reviewers with distinct lenses** (correctness/reconciliation · state & lifecycle · test quality · security), not as repeated serial rounds with one generic prompt. Keep a written round scorecard — total findings and HIGHs per round: a round returning only LOWs is a stop (defer them with written reasons), and a FLAT rate over 3+ rounds (measured: 5,6,4,4,4,6 / 2,2,1,1,1,2) means grinding has reached equilibrium — your fixes add reviewable surface as fast as the panel consumes it; stop, or replace the patched region with one deliberate rewrite reviewed whole. Never predict that the next round is clean, and a clean LENS is not convergence (lifecycle approved four rounds running, then produced a genuine HIGH).

**Why.** Serial rounds are partly irreducible — a fix *creates* the surface the next round finds, so you cannot review a fix that does not exist yet. But identical-prompt rounds plateau fast: measured on one build, spec rounds 4-7 returned exactly 1 finding each (2 LOW), while a single review of the real diff returned 7 including 2 independently reproducible bugs. Value concentrates in reviewing **executable code**, not more prose rounds. Diversity also beats repetition on the same artifact: a reviewer that just approved something is poorly placed to attack it, whereas a different lens found that a fix written *for an earlier finding* mutated a ref during render (which React can abandon mid-transition).

**Who writes the fix.** Codex authors the fix for its own finding by default when it is mechanical (`run-codex.sh --write`, linked worktree, one finding per run) with Claude reviewing the diff — independence holds, inverted — and the two fix streams run in PARALLEL (Codex on a sibling worktree/temp branch off the round's HEAD, merged back by Claude), so the fix stage pipelines instead of serializing. Route MECHANICAL findings there (substring→exact assertion, an uncovered shape, a missing noun); keep JUDGMENT with Claude (reject the finding, choose between designs, decide what a sentence may claim), because "reject" is the right answer often enough to matter and a plausible diff makes it harder to reach. **But route by the round's shape, not reflexively**: the per-run cost is near-fixed (~60–70% of writing it yourself PLUS ~10 min wall-clock for the gates and independent review), and one finding per run means N mechanical findings are N SEQUENTIAL runs — do it inline when it is the round's only finding, trivial, or the mechanical queue would outlast the judgment stream. The routing UNIT is the sub-task, not the finding: write the routing table BEFORE the first fix lands, and carve each judgment finding's mechanical tail (a golden regeneration, a guard copied from an existing rule, a test scaffold) onto the Codex queue so it runs under the judgment work — the judgment stream is the critical path and it shortens only by moving work OFF it (measured 2026-09-01, your-module r1: 17 accepted, 7 mechanical ones ran on Codex in parallel, then the last three judgment items each carried such a tail and ran it serially on the judgment seat). A "mirror X inline in the UI" finding is an IMPORT of the existing predicate, never a second copy (`[[mirror-a-gate-at-its-exact-scope]]`). Regardless of author: **mutation-verify every FIX, not just every test** — a proposed test is not a verified one (one harness passed with the production guard deleted; two fixes shipped with NO test and were caught only by mutating them; two tests passed for the WRONG reason — a fixture side-path filed the asserted artifact, a guard sat where the throw does not happen), and a mutation that does not kill the test is a finding about the test — and **assert the edit target exists before replacing**, since a silent no-op reports success from the file write, not the match.

**How to apply.**
- Budget rounds to the artifact: converge the spec/plan enough to be coherent, then get to code — the diff review is where the bugs are.
- Per round, fan out 2-4 lens-scoped prompts concurrently; each reports only defects visible through its lens.
- Carry an adjudication list into every prompt (`do NOT re-report X`) so attention goes to new ground.
- Stop when a round yields only LOWs; a plateau is a signal, not a reason for another identical pass.
- Micro-review the fix commits with the counter-party (`<prev-round-HEAD>..HEAD`, sol; solx on money/lifecycle) BEFORE launching the next full panel, scoped to the commits that have not yet had a counter-party review — the Claude-authored judgment fixes; a Codex fix was reviewed hunk by hunk at merge, so a round whose fixes were all mechanical goes straight to the panel — measured on one branch, three rounds' findings were defects in the previous round's own fixes, including a HIGH after two zero-HIGH rounds; catch those in a micro-loop, not a full round. The micro-pass never replaces the confirming full-range round.
- Give every round the REACHABILITY FRAME with the diff (who writes this column/field, what the schema and callers guarantee, whether the value is displayed or acted on). Without it a reviewer correctly generalises the codebase's own documented past defects onto inputs that cannot occur — the file's "this table is not STRICT so a row can hold junk" comment, written for a real crash, produced two rounds about a fractional value in an `INTEGER NOT NULL DEFAULT 0` column only our own `= 0` / `= n + 1` statements write.
- Demand the WRITE PATH for any finding about bad stored or incoming data: name the code that produces the bad value, or the finding is declined and recorded. **Accepting an unreachable finding manufactures the next round's findings** — normalising an impossible value added a normaliser, and the following round reviewed the normaliser (floor vs round). That is a treadmill you built, not convergence.
- Reproduce a reviewer's behavioural claim yourself before acting — and reject it with written evidence when the codebase documents the behaviour as deliberate. A claim can be right about the risk while its recommended fix is wrong: never tighten a guard to match a validator whose acceptance set you have not measured (one proposed tightening would have re-introduced a narrowing bug from two rounds earlier); record the rejection in the spec.
- **A mismatch finding names a fact; it does not name which side is wrong.** When a lens reports "the code disagrees with the spec/plan", the remedy has two directions and choosing one is a JUDGMENT call — re-measure the code before taking either. A low-tier lens reliably picks the wrong one, because **a converged-looking document is a strong attractor**: the more polished and cross-referenced a spec is, the more a reviewer treats it as the artifact and the code as the deviation. It is the reverse. **A spec is a claim; only the code is an artifact.** Measured 2026-08-28 (your-module): a round-1 traceability lens (gpt-5.6-luna/low) filed a HIGH telling the implementation lane to DROP a real ninth helper from their plan "to make the plan match the spec" — the spec's closure clause was the six-round-old bug that had been hiding that helper, so obeying the finding would have re-buried the defect the previous round had just dug out. The lane accepted the FACT (the two disagree) and declined the REMEDY (conform to the doc), which is the correct split. In the same arc a spec guard read "exactly the eight files/lines"; the code had 8 files but **13 import lines**, and an implementer trusting the sentence would have built an 8-entry allowlist that fails on correct code — then "fixed" it by deleting the line pin, i.e. the evasion the guard existed to close.
- Corollaries: accept a mismatch finding's fact and adjudicate its direction separately, in writing; when the doc loses, correct the doc in the SAME round rather than carrying a known-false sentence forward; and once you have corrected it, say so downstream — your own freshly-landed round is now just another claim, so tell the consuming lane to report back if their measurement disagrees rather than conforming to your text.
- When successive findings on ONE artifact are each a new evasion of the previous fix, assert the PROPERTY instead of the SHAPE (the engine's own statement trace, post-interleaving state) — shape assertions invite bypasses forever; where no property-level assertion exists, accept the limit, record it in the spec, and stop paying.
- Watch the wall-clock: a parallel fan-out can outrun a foreground shell timeout, so launch it as a tracked background job.
- **No round-varying fact may live in a shared prompt fragment.** A HEAD SHA baked into a reused facts/ledger block silently voided a whole round: all three reviewers OBEYED the stale `<structured_output_contract>` over the fresh task line and reviewed the previous range. Emit the contract (SHAs, file lists) per round from live `git rev-parse`; the caller-side `reviewed.head` echo check is the tripwire that catches it — never skip it on an "obviously fine" round.
- End on a WHOLE-DIFF lens: twice now, three clean narrow lenses were followed by a whole-diff pass finding a real regression (a planner regression; a cross-file contradiction). The confirming round that closes the gate should always include one.
- The worst bugs live at SEAMS between individually-correct functions, invisible to either side's tests: on PR #229 (2026-08-03) a deterministic re-render silently overwrote the LLM writer's output while keeping its provenance stamp, making the whole feature a permanent no-op. Ask what happens when two correct components meet on live state — and don't predict a clean round from a green suite: that PR ran 23 rounds each finding a real HIGH (suite green every round) before round 24 was clean. Verify every fix RED against the prior commit before trusting it.

**Document stages count too (2026-08-19):** the parallel-lens rule applies to SPEC and PLAN reviews, not only code diffs — a serially-reviewed spec took 9 rounds while the plan, reviewed by a concurrent semantic + traceability panel, converged in 4 on a comparable finding load. Union the panel's findings, fix once, confirm once.
