Before concluding "X never ran / never happened" from a query returning zero, ask what artifact X *actually happening* would produce, and confirm your probe would have seen it.

**Measured 2026-08-11.** A live §11 redisposition migration was declared "never ran — the DB is in a clean pre-migration state, safe to resume the company" on the strength of `events WHERE type LIKE 'redisposition%' = 0`, all time. But the archive path writes **no events at all**, so that probe could not distinguish "never ran" from "running right now". It was running — had been for 14 hours, had archived 2,501 names, and was ~58% through. The discriminating artifact was `dp_screen_receipts.detail_json origin='redisposition'` (`redisposition.ts:604`, written on every applied archive). Resuming on that conclusion would have aborted the live run at its quiescence precondition (`redisposition.ts:99`).

**Why:** an absence proof is only as strong as its probe's discriminating power, and zero rows from the wrong table look exactly like zero rows from the right one. The defect is invisible in the result — it lives entirely in the choice of artifact, which is why it survives review and gets repeated with confidence.

**How to apply:** name the write site (file:line) that a positive case would produce, confirm your query reads THAT artifact, and state the write site when reporting the absence. If you cannot name it, you have not disproven anything — say "not established" rather than "did not happen". Apply this hardest before irreversible or outward-facing actions, and when RELAYING someone else's absence-proof: reproduce it against the discriminating artifact before amplifying it, because amplification is how a weak probe becomes a green light someone acts on. **A stated intention is not an accomplished fact, and a peer's account of a third party is hearsay.** Measured 2026-08-21: one session read another's handoff line "I DROP the job on dispatching you" and relayed it as *having dropped*, asking that three runbooks be rewritten to stop addressing a seat that was in fact `state=working`, `tempo=active`, with a transcript growing 56 KB per 100 s and an `updatedAt` LATER than the claim — leaving two live sessions holding one merge runbook for a merge that restarts production. Positive proof of life (an advancing state field plus a growing artifact, read twice) beats any assertion of absence, so measure a liveness claim about a third party yourself before writing it into a file, and refuse to propagate one on a peer's say-so — the refusal is what stops a bad fact reaching every runbook that trusts yours. This applies to TEXT SEARCHES as literally as to queries, and the probe does not end at the pattern: **any transform between the artifact and your eyes is part of it** — `cut -c`, `head`, a column limit, a preview pane, a `find -maxdepth` cap. Each converts "present but past my cutoff" into "absent", and none announces that it did. Measured 2026-08-21, twice within the hour: a case-sensitive grep for a bullet reading "Decide on INSTANCES" returned empty; then a `cut -c1-230` hid a clause beginning past character 900, one step from filing "your durable edit silently failed" against a file that was correct. Case-sensitivity at least fails inside the probe; truncation fails BETWEEN the probe and the reader, which is worse. Measured 2026-09-03, the depth form: `find ... -maxdepth 4 -name 'hookify.*.md'` returned 0 and I wrote "the plugin has no rules and does nothing" into two memories — a worktree sits at `<repo>/.claude/worktrees/<name>/`, putting its `.claude/` at depth 5, and a depth-free find returns 18. The lane file had already recorded three. **When the subject is TRACKED, ask git, not the filesystem** — `git ls-tree -r origin/main <dir>` has no depth, no cwd and no glob to get wrong, and it answers about the shared truth rather than about one checkout. So when a probe reports absence the next move is not a better pattern — it is **reading the artifact whole wherever it is small enough to read whole**, and zero-testing the entire pipeline rather than the pattern alone. Extends [[verify-claims-against-artifacts]] from "don't trust a success flag" to "don't trust a silence".

**When quiet cannot distinguish two worlds, do not reach for a longer look — reach for the case that would have to be LOUD.** Some subjects are structurally incapable of testifying: a rate-capped session is idle awaiting an input event, not retrying, so it stays byte-identically flat whether the cap lifted or not, and watching it longer only buys a more confident wrong answer. Switch subjects to one whose success is unmissable. Measured 2026-08-21: "did the account switch clear the cap" was unanswerable from the silent capped sessions, but six successors dispatched *after* the switch grew from 18–31 to 46–145 real assistant turns with **zero** synthetic (harness-error) turns — proof the new account spends. Note what that does and does not settle: it collapsed the question from "did the switch work" to the far narrower "does a PRE-EXISTING capped session recover when nudged", which still only a nudge answers. State the residue explicitly, because a loud positive tempts everyone to retire the whole question. See [[session-reachability-is-status-not-state]] for the three-state form (dead / reachable-but-capped / live) and the `model=<synthetic>` marker that identifies a capped turn.

**The same defect runs the other way: a probe that cannot report FAILURE.** Absence proofs are the famous case, but any check whose failure branch is unreachable reports the answer you expected for every input — and success reports are trusted harder than silences. So for any check that reduces to a boolean, **run it against a control that forces the opposite answer before believing it.** Measured 2026-08-22, four in one hour: a watcher lease "proved held" by `flock -n`, which **does not exist on macOS** — it exited 127 into a branch reading non-zero as held, printing `held` for every input including no watcher at all; a liveness probe printing `no transcript` for a transcript growing 25 KB/min, because macOS `wc -c < file` emits leading spaces and the `isdigit()` guard fell through to the failure branch; `handoff.sh --watch-once` reporting `working, heartbeat 1m old` for a watcher that was never started, since the same empty `watch_gen` that kills the watcher makes the health probe answer on its behalf — the stall detector fails OPEN exactly when nothing is watching; and `handoff.sh` reporting `session X is not listed` for a session that was listed and running, because it compares an ANSI-wrapped id parsed from colourised output. The sound form takes seconds: probe the real subject, then a control that must answer the other way (a fresh unlocked file must read `free`, a nonexistent path must exit non-zero *without* printing `held`). **Distrust hardest the probe you wrote yourself ninety seconds ago to confirm something you already expected** — it got the least review and carries your expectation in its failure branch. When a tool reports success *or* failure, ask what the other answer would have looked like and whether your setup could produce it. **And the control must share the probe's pattern CLASS, or it validates the mechanism while the defect sits in the class.** Measured 2026-08-23: a case-SENSITIVE `grep -E` for answer markers on a decision page returned 0 where the correct probe returns 3, and the accompanying control — a `the`=33 hit-count — fired perfectly, because it tested *that grep runs and can match*, never *that this pattern is case-correct*. A passing control made an unsound probe look sound, and the 0 read as "no answer present", which happened to be the true answer by luck. So build the control by mutating the SAME dimension the probe depends on (case, anchoring, word boundary, multiline, the transform chain, and the FILE SET the glob actually matches), not by proving the tool works at all; and for text, default to `grep -niE` rather than `grep -E`. **And choose the control's DATA so a wrong probe gives a DIFFERENT answer** — a control built on degenerate or self-consistent values passes under the very corruption it exists to expose. Measured 2026-08-24: a greedy `sed -nE 's/.*([0-9]+) passed.*/\1/p'` read the CI summary `10 passed, 0 failed, 6 pending, 16 total` as `0/0/6/6`, because the greedy `.*` eats every digit but the last — and the forced-all-green control `16 passed, 0 failed, 16 total` fired GREEN anyway, since `6 == 6` holds under the same corruption. The control shared the pattern class and still certified garbage. So assert the parsed VALUES against known-correct ones (10/0/6/16) rather than merely that the green branch is reachable — the same requirement [[plan-assertions-need-reachable-alternatives]] puts on fixtures (never a degenerate point), applied to controls. **A false 0 is at its most dangerous when it argues you into WITHDRAWING a true claim.** Measured 2026-08-23, same lineage, different seat: a probe counting stale watcher-lease files globbed with a leading dot the filenames do not carry, returned 0, and the seat briefly retracted a correct stale-lease finding on it — the real count was 17, every one of them zero bytes. Retraction feels like rigour, which is exactly why it needs the same both-ways control as an assertion: run the glob against a path you KNOW holds matches before you believe it holds none, and see [[re-read-cannot-tell-wrong-from-acted-on]], because "my probe now says no" and "I was wrong" are different findings.

A probe can also be pointed at a file the action never writes: `git -C <linked-worktree>` writes that worktree's **own** `FETCH_HEAD` (`.git/worktrees/<name>/FETCH_HEAD`), so the top-level `.git/FETCH_HEAD` reads "no fetch" no matter how many fetches ran — two sessions cited it as proof while a peer fetched every ~3 minutes.
Before believing an absence, name the exact path the positive case writes, and re-check that your own regex is not matching a COMMENT describing the defect instead of the code doing it (strip comments, then control-test a known-positive and a known-negative file).

**The RENDERER is a transform too — it writes bytes you never authored, between your source and your regex.** Measured 2026-09-03: an acceptance criterion asserted `/Counts as of ([^<]{1,40})/` against a live server-rendered page and read `ABSENT`, failing a shipped fix that was working perfectly. The caption is JSX with an expression child (`Counts as of {fmtAgo(...)}`), and React's SSR emits a `<!-- -->` separator between a static text node and an adjacent expression — so the byte after the phrase is `<`, and a `[^<]` class can NEVER match a correct page. The probe had no reachable success branch, and its failure looked exactly like a product defect. The repo's own unit test never saw it because `textContent` skips comment nodes — i.e. the DOM reader and the byte reader disagree about what the page says, and only one of them is what a regex sees. So: **anchor a probe on a stable identifier (a `data-testid`) and read the element, never on prose spanning a static/dynamic boundary**; and when a rendered-output probe reports absence, dump the RAW bytes around the phrase before believing it. This is [[enumerate-the-transforms-between-authoring-and-use]] applied to markup: framework-inserted comments, whitespace normalisation, HTML entity escaping and attribute reordering all sit between what you wrote and what you grep. The two-sided control that settles it costs seconds and must run on the REAL captured bytes: the matcher must return the value on the live page, return null when only that element is deleted, and — decisively — the OLD matcher must be shown reading ABSENT on those same correct bytes, which is what converts "it passes now" into "the probe was wrong then".
