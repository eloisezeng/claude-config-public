When a guard enumerates sites and asserts each one is correct, the predicate is doing all the work.
**A text-level predicate — "the enclosing function mentions `X`" — is not a test that `X` was applied to the value that matters.**
It is satisfied by a site that mentions `X` once and leaks the value somewhere else, which is precisely the shape a half-done fix has.

**Measured 2026-08-30, your-module phase-0 impl, CI red cycle 1 (finding F3).**
Four test sites spawned a child `vitest` and asserted on its stdout; CI colourises, so all four needed `stripAnsi` and a no-colour env, and only one of the four had it.
The fix went into one shared module and a guard was written to keep it there.
The guard's first predicate was `enclosingFunctionText.includes('stripAnsi')`.
A control that mutated a COPY of one site — stripping the wrapper off ONE of its two captures while leaving the other wrapped — **survived**: the function still mentioned `stripAnsi`, so the guard still passed on a site that was now broken.
Only the structural predicate caught it: parse the file, find every capture expression reachable from the child's output, and assert each is lexically inside a `stripAnsi(...)` call.

**How to apply**
- State the property you actually want in one sentence, then ask whether your predicate would separate a site that HAS it from a site that merely NAMES it. If both read the same to the predicate, it is a mention test.
- Prefer structure over text: parse and walk. "Every text-producing capture is inside a `stripAnsi` call" is checkable; "the function mentions `stripAnsi`" is not.
- **The mutation control is the only thing that tells you which one you wrote.** Arm the *partially* broken variant, not the fully broken one — a fully broken site fails both predicates, so it proves nothing about the difference. See `[[a-surviving-mutant-may-mean-the-property-is-unobservable]]` for the other reading of a survivor, and `[[absence-needs-a-probe-that-could-see-presence]]` for the general form.
- Mutate a COPY and assert every tracked file unchanged in the same script — `[[never-arm-a-fault-in-an-auto-syncing-tree]]`.
- Derive the site list from the repo (`git ls-files`), never from a hand-written array, and write the derivation's BOUND next to the assertion: which sites it deliberately does not sweep, and why — `[[a-guard-must-be-satisfiable-not-just-failable]]`.
- **A rule enforcing only the NEGATIVE half leaves the positive half unmeasured, and the census cannot be taken with a grep.** A repo rule read "goldens are checked-in files, never a snapshot; no module writes into the goldens directory, and the regeneration recipes live in DOCBLOCKS" — the guard proved no module WRITES a golden and nothing proved a golden CAN be regenerated. A golden with no recipe is then regenerated by whoever next needs one, from whatever they infer, and **a wrong inference reads green for ever**; the same repo had already found and fixed a BROKEN regeneration recipe, so a recipe that exists is not a recipe that works. Measured 2026-09-04 over the 17 tracked golden files, two patterns over one tree: a strict "does some reader carry a heading-shaped regeneration instruction" matched **1 of 17**, and that one was the file the same commit had just written — no mention-level pattern can tell a recipe from a passing reference to one, which is this memory's rule applied to documentation. Enforce the positive half by REGENERATING in CI and diffing, not by grepping for the word.
- **A SIMULATION inherits the gate's predicate, so simulating a change under the OLD predicate is fail-open on exactly the thing you are changing.** The practice "simulate the stricter set against the artifact BEFORE adding it" is itself satisfied by this class. Measured 2026-10-29 on a completeness gate whose half A looked each frozen finding id up with an any-line `grep -E "(^|[^A-Za-z0-9-])${id}([^A-Za-z0-9-]|$)"` over a markdown ledger: adding six ids and simulating first read **55/55 GREEN**, and two of the six had NO row of their own — they existed only as sentences inside two OTHER findings' rows ("...is new finding **G8**, deferred"). The gate was matching a mention, the simulation copied the gate, and the honest-looking order (simulate, then add, then write the rows) would have been green at every step. Tighten the predicate FIRST — here, `^\|[[:space:]]*\*\*${id}\*\*[[:space:]]*\|`, a ROW KEY, required exactly once — and only then simulate the addition; the mutant that proves which predicate you wrote is the OLD artifact, which must go red naming exactly the added ids and nothing else (it did: `RED ... G8 G9`, 53/55).
- **Build the simulator by EXECUTING the gate's own block, never by copying its predicate.** The existing simulator held a hand-copied loop and a hand-typed id list, so it could not have shown this at all. Extracting the gate's half-A block at run time (`sed -n "${start},${end}p"` between its own `IDS="` line and the `fi` that closes it, with `say`/`good`/`bad` stubbed and `LEDGER_TEXT` preset) makes the simulation and the gate one rule by construction — the same reason a guard and its truth table share one function.
- **A hand-typed frozen set can be checked BOTH ways against the artifact without letting the gated party author its verdict.** The usual reason a closure set is typed rather than derived is sound — deriving it from the file being checked lets a dropped finding drop out of the closure with it. But the reverse direction is still free: read the artifact for NAMES only ("every row key the ledger publishes must be in the frozen set") and keep the OUTCOME decision in the gate's own loop. One-way checking is what leaves a finding written into the ledger and never added to the set with no diff line to point at — `[[a-gate-may-not-read-its-verdict-from-the-gated-party]]` · `[[replacing-a-list-with-a-glob-changes-the-set]]`.
- **Going structural ONCE is not enough: each repair can fail open in a new form, so the fix is to fail CLOSED on every input the predicate cannot account for.** Measured 2026-10-29 over four review rounds on one shell guard, where the same rule was repaired three times and each repair accepted a NEW escape hatch. It began as `any(WANTS in g for g in guards)` — a mention — which `-eq 1` → `-eq 0` defeats. Repair 1 parsed the comparison and required it positive; that accepted THREE defective conditions: `|| "$PREWARM" -eq 1` (installs in the posture that must not), `&& "$PREWARM" -eq 1` (skips it in the posture that must), and `== 01` (integer-normalised to 1, but bash compares the string and it is false for every real value). Repair 2 went semantic — bash EVALUATES the condition at both flag values, and the condition may name no other variable — and that still failed open on `|| $((PREWARM)) -eq 1`, because a name-scanner matching `$NAME`/`${NAME}` cannot see an arithmetic expansion AND an unset variable in arithmetic context is 0, so the isolated evaluation reads true-at-1 / false-at-0 exactly like the correct condition. Two further hatches (command substitution, backquotes) were being refused BY LUCK — the truth table caught them for being true at flag 0 — while the scanner reported "only the flag" for all three; luck is not a rule, and a scanner that silently answers "no other variables" for a form it cannot parse is worse than no scanner.
- So: **enumerate what your predicate can parse, and refuse everything else by name.** For shell that is arithmetic expansion `$(( ))`, command substitution `$( )` and backquotes, indirect expansion `${!x}`, and special/positional parameters (`$?`, `$1`, `$#`) — anything that is not a plain variable read. Refusing is the honest answer: a condition needing them is not one the guard can adjudicate. A fail-closed rule's failure mode is a VISIBLE false red; a fail-open one's is a silent false green, which is why this is the structural end of the class rather than another predicate. Keep the rule as ONE function the guard and its truth table SHARE, so the two cannot drift, and keep the table satisfiable in both directions — mine ran 15 rows, 4 accepted and 11 refused, asserted with 0 mismatches. The tell that you are still in this loop at all: the second repair of one rule. If a repair is the second, write the fail-closed version instead of the third predicate.
