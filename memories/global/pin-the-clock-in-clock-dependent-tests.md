---
name: pin-the-clock-in-clock-dependent-tests
description: "Any test of date/time-dependent behaviour must pin the clock — otherwise it passes until the machine crosses the boundary the feature is about"
metadata:
  type: feedback
scope: global
---

If the behaviour under test reads the clock — a rollover, an expiry, a countdown, a "today" window — the test must pin that clock (`vi.setSystemTime` / equivalent) in setup, not rely on ambient time. A fixture holding a hardcoded date is a time bomb: it is a normal case until the machine crosses the boundary, then silently becomes the *other* case.

**Why:** on 2026-08-07 a card compared its server-rendered UTC date against the client's current UTC day to restore a daily allowance after midnight. The tests pinned fixtures to `'2026-08-07'` and ran against the real clock. They were green for hours, then went red mid-session with no code change — the machine had passed 00:00 UTC, so every fixture became a rollover case and two byte-for-byte copy assertions collapsed. In CI that is an overnight red build with an empty diff, which reads as flakiness and gets re-run rather than fixed.

**How to apply:**
- Pin in `beforeEach` for the whole file, at a time that makes the copy deterministic (e.g. mid-afternoon UTC so a countdown reads in whole hours), and restore real timers in `afterEach`.
- Tests that need a *different* instant set their own inside the test; a file-level pin does not stop that.
- Write the boundary test so it fails against the lazy implementation: mount *before* the boundary with current data, then advance time across it while mounted. Asserting only that already-past data renders correctly passes against a check that runs once on mount and never again.
- Beware the inverse: a globally pinned clock makes server and client agree by accident, hiding hydration bugs. Assert the pre-effect state separately (`renderToStaticMarkup` runs no effects) so "no clock-derived text initially" is actually proven.
- Do not pin JS time when the same test's data comes from a database using the OS clock (SQLite `date('now')`) — you desynchronise the two and manufacture a failure. Let both use real time, or control both.
- **A test that mixes an injected fixed clock with `Date.now()`-relative fixture anchors does not flake — it EXPIRES on a computable date. Derive that date before doing anything else**, because it decides the response: a flake gets a retry, a bomb gets fixed now. Solve the inequality between the fixed instant and the drifting one; the answer is a calendar date. (2026-08-09: an agent injected at a fixed `2026-08-07 00:10` had its history anchored at `realNow − 2d`; passing required `realNow < 2026-08-09 00:10`, so the suite went permanently red that morning and read as flake.)
- **Prefer restoring a file's existing convention over adding a second mechanism.** That fix was a *deletion*: a helper in the same file already re-anchored every row it wrote onto the injected clock, with a comment giving exactly this reason, and the offending block overwrote those correct anchors. Two mechanisms anchoring the same rows is how the next person reintroduces it.
- **Fixing the red instance is not curing the class — measure the rest and say so.** Simulate time passing (shift the fixture calendar backwards) and re-run: if other tests red, name them, date the next failure, and hand the class cure to its own piece of work rather than implying the file is safe.
- **When you re-anchor a fixture calendar to the real date, the direction matters.** Fixture "nights" must sit in the real PAST if the DB stamps rows from its own clock: a fixture night *ahead* of the real clock gives a row written "tonight" a real stamp EARLIER than its own history, inverting any strictly-earlier ordering rule. Anchor so the days in use are a few days back, and pin that with an assertion.
- **A real-date-anchored *local* calendar is a seasonal reprise of the same bug** — it crosses DST twice a year, so civil days become 23 or 25 hours (21 under a large offset move, and some zones have no valid midnight at all). Fixtures that state elapsed time as wall-clock hours ("started 01:00, invoked 12:00") silently stop testing what they name: a 22.5 h gap becomes 19.5 h under a 3-hour advance and no longer exceeds a 20 h cap. **Pin the process timezone to UTC** for such a file (before capturing the calendar base, restored in `afterAll` — pools recycle processes across files). UTC has no transitions, so the arithmetic is invariant *by construction*, and it usually matches CI. Tests that genuinely need a real zone set and restore it themselves.
- **Reviewers will enumerate zones and dates forever; that is the treadmill, not the fix.** Rounds citing counterexamples from 1890 mean the frontier is moving, not closing. Assert the property (no DST in the fixture zone; a stated cap instead of one inferred from wall-clock arithmetic) and the whole family dies at once — including the sibling fixtures you had not patched yet. Adjudicate unreachable dates as unreachable: an anchored calendar producing `today−N … today` cannot reach 1899.
- Build a shifted instant with ONE constructor applying the offset to the date field (`new Date(y, m, d + offset, h, min)`), not by constructing the hour then `setDate`. The latter resolves the hour against the BASE date, so a nonexistent hour there corrupts a target date whose own hour was fine.
