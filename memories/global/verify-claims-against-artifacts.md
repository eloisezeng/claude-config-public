Don't conclude a step "succeeded" / "is done" / "works" from a **proxy** — a `status` column, an exit code, a "✓ done" log line, or your own first-read mental model of unfamiliar code. Those are *claims*. Verify against the **artifact** the action was supposed to produce.

**Why:** A prior session told the user the `.com` zone download "succeeded yesterday" because the run row read `status='succeeded'`. It hadn't — a failed CZDS download is handled as *inert* (the agent logs an alert and resolves cleanly), so the run still stamps `succeeded`. The disconfirming tells were right there and ignored: **0-second** duration (a real run is ~29 min), **no** snapshot file, `name_count=0`. The wrong conclusion got frozen into a handoff as fact and surfaced to her; she had to correct it across several turns. Same class as this project's recurring "reasoned about the code, not the running instance" misses — a success enum is not evidence the work happened.

**How to apply:**
1. For any "did X work?", the answer is the **artifact**, not the flag. A success enum → cross-check the row/file/count it should have produced (e.g. snapshot file exists **and** `name_count > 0` **and** non-instant duration). Exit 0 → read the output. "Tests pass" → read the actual run summary.
2. **Distrust enums that mean several things.** `succeeded` often conflates did-work / no-op / tolerated-failure / gated. When you see one, ask "what would a *real* success have left behind?" and go look for exactly that.
3. **First time reading unfamiliar code or live state, findings are hypotheses, not facts** — until checked against evidence. Never freeze a guessed root cause or outcome as fact, especially in a handoff; separate "verified" from "inferred." If context is running out, label the guess as a guess rather than asserting it.
4. When the user says "I thought you said X worked," re-open the evidence before defending — they are usually right that a claim outran its proof. Own the miss plainly.
5. **Check your probe has DISCRIMINATING POWER before believing its answer.** Ask "would this query read differently under the opposite hypothesis?" — if not, a zero is not evidence of anything. Measured 2026-08-11: a session concluded a live migration "never ran, safe to resume" from `events LIKE 'redisposition%' = 0`, but that path writes no events at all, so the probe read zero either way; the real artifact was `da_screen_receipts.detail_json origin='redisposition'` (2,501 rows). The correction then overshot to "running RIGHT NOW" off a recent-timestamp read alone, when a **repeated** sample (MAX(id) frozen across three reads) plus a process enumeration showed it had stopped. Both errors were one cheap discriminating measurement away, and each pointed at an opposite, wrong action.
6. **Attribute a signal to its EMITTER before inferring from it.** `grep` for what actually writes the row/event/log line; do not reason from its name or its timing. Measured 2026-08-11: two sessions independently read a `buy_card_default_restamped` event landing seconds after a migration burst as "the migration reached its cards phase, so it completed" — one grep showed the migration never emits that event at all (a worker sweep does), which flipped the same rows from evidence-of-completion to evidence of the very worker activity that aborted the run. Correlation in time is not authorship. Related: an early `return` is indistinguishable from success from the outside — capture an operator script's stdout and exit code at the call site, because the reason lives in the report it printed and nowhere else.
7. **A mock of the thing under test cannot witness what the thing under test does.** Before trusting a test, ask what the mock REPLACED. Measured 2026-08-11: a money connector had many "exactly one fetch call" assertions via `vi.stubGlobal('fetch')`, and every one was structurally blind to native fetch's own redirect-following — the stub replaced the machinery doing the extra request. A real HTTP server on a real socket showed ONE purchase putting `command=register` on the wire TWICE and succeeding. Same shape as a fixture derived from the constant it protects, one layer down. Any invariant about how many requests/writes/calls actually reached the outside world needs the real transport, not a double.
8. **Chain a state-changing step on the producing command's EXIT CODE, never on a grep of its output.** `vitest run | grep passed && git push` pushes red: grep exits 0 because "passed" lines exist even in a failing run, and a pipeline's status is the LAST command's. Capture `RC=$?` from the runner itself and branch on that (`vitest run > f 2>&1; RC=$?; [ $RC -eq 0 ] && git push`). Measured 2026-08-12: two red pushes in one session, both via output-grep chaining; zero after switching. Same class one level down: a hook/wrapper that swallows the runner's status re-introduces the bug.
9. **Timestamp your own actions when you share a system with other writers.** When a peer asked whether my read-only run had caused a write burst, memory of "I ran it after that" was not proof — the artifact mtime, a bracketing query's stamp, and an unchanged MAX(id) across later samples were. In a multi-session repo, expect to have to exonerate yourself with evidence.

10. **A DESCRIPTION is a claim, whoever is describing — a careful peer, or you.** The artifact-trust rule is usually applied to *fields* (`status`, `detail`, a log line) and then silently dropped for *prose from a trusted source*. Measured 2026-08-22: supervising a fleet, I applied it rigorously to seats' self-written `detail`, to a peer's md5 claim, and to a peer's exit-code claim — then took that same peer's one-line characterisation of a lane ("I'm ADDING a second seat, not swapping") as the fact, and predicted a live seat was about to be wrongly retired. It had stood down sixteen minutes earlier; its own last turn said `HANDED OFF`, and its runbook carried a `SUCCESSOR DISPATCHED` section. The peer's wording was bookkeeping, not lane semantics — it was not lying, and it had not read the transcript either. **A peer's description of a thing is exactly as self-written as that thing's own `detail`, and inherits none of the authority of the artifact it describes.** Ask "who has actually opened the artifact?" — if the answer is nobody, a confident description from a careful colleague is still an unverified claim. Applies to your own earlier summaries too: a fact you asserted last turn is a claim once it is out of the window. Settle it by ORDERING (the artifact's timestamp against the claim's), which also distinguishes "I was wrong" from "I was right and someone fixed it" ([[re-read-cannot-tell-wrong-from-acted-on]]).

11. **A count is not a measurement until its RULE is stated — and "does not reproduce" is a claim about running THEIR rule, not yours.** Measured 2026-08-28 (your-module §13): three passes over a **byte-identical** artifact produced 33/49, 35/54 and 35/56 imports, and every disagreement was *definitional*, never observational — one rule counted only alias-form specifiers (`@/plugins/…`) and could not see seven relative-form imports; the other required `import` and `from` on one physical line and could not see two multi-line specifiers. Close both blind spots and the methods converge exactly. I published "r3's 35 does not reproduce" when what I actually had was "my rule differs", which is a strictly weaker fact, and a peer had to withdraw the parenthetical for me. **Before disputing someone's number, re-run THEIR rule, not a rule of your own that yields a different number** — a mismatch between two counts is evidence about the two definitions until you have shown they are the same definition. Publish the predicate beside the figure ("every import line whose specifier resolves under `plugins/`, both alias and relative form, tests excluded") so the next reader can tell disagreement-about-the-world from disagreement-about-the-question. Corollary when you are the one confirming: state which half you actually ran — reproducing a direct count does not confirm the transitive figure printed next to it. **And the predicate you write down is itself an artifact — stating it is necessary and not sufficient.** Measured minutes later in the same arc: the predicate I published said `@/` resolves to `src/`, but the repo's tsconfig maps `@/*` to the repo ROOT, so my walk silently dropped six real intra-module edges. It happened not to move the figure (re-run with the mapping fixed: identical), but nobody knew that until it was re-run — a stated rule that has never been executed against the thing it describes is a claim like any other. Check the predicate the same way you check the count. Corollary about inferring backwards: a peer reasoned "your number is right, so your code cannot be doing what your prose says" — wrong, because the direct count never flowed through the resolver at all; prose and code agreed with each other and both were wrong about the repo. **Do not infer a mechanism from a number without reading the mechanism.** And the constructive half, from the third rule in that arc: two of the three wrong rules failed by matching too NARROWLY (alias form only; `import` and `from` required on one physical line) and the third by matching too BROADLY — any string literal also swallows `readFileSync('../../plugins/…/schema.sql')`, a build-time coupling of a different KIND, not an import edge. So "broaden the pattern" is not the fix; the only rule that gets all three right is the specifier's POSITION in the syntax tree. **When a textual rule keeps needing widening, the defect is that it is textual** — move to the parser, and keep the three failures as the walker's negative test cases. Same class as [[a-guard-must-be-satisfiable-not-just-failable]], one level up: there a bare count stood in for a derivation inside a guard, here inside the prose that audits the guards.

- **Never infer another implementation's MECHANISM from its output.** A number that looks impossible under someone's stated rule usually means your model of their code is wrong, not that their code contradicts their prose. Measured 2026-08-28: a peer's resolution rule was wrong as stated AND its code matched the prose exactly — both wrong about the repo — yet its figures were right, because its direct detection short-circuited before resolution ever ran. My "its code cannot be doing what it says" was reasoning from MY architecture applied to theirs. Read the mechanism, or run a control that forces the outcome you are predicting; the class migrates into the instrument you audit with.

- **A fact resting on ONE probe is not established, however direct the probe looks — cross-check it against a measurement you already hold.** Measured 2026-08-28: two consecutive `git show "$C:path"` calls returned COMMIT-DIFF output instead of the blob, which at face value placed an import inside a file that does not contain it and would have landed a fabricated refutation of a peer. Caught only by inconsistency with an earlier enumeration of my own that would have had to list that file. An earlier measurement that must agree is the cheapest control there is; prefer literals over shell variables in any probe you will publish from, and record an unexplained probe failure WITHOUT inferring its cause — but *not inferring* a cause is not the same as *leaving it unexplained*. Measured hours later by the second seat in that arc, in two commands: `git show <rev>:<path>` returns the blob, `git show <rev>` alone returns the commit diff, and the very import line that had looked like a refutation greps **1** out of the diff and **0** out of the real blob. So the argument reached git as the rev with its `:path` suffix gone; the text was real, its SUBJECT was another file. The mechanism was then CLOSED the same day, and it was the shell: zsh applies a history modifier to an UNBRACED parameter expansion, so `$C:src/...` parses as `$C` plus the `:s` (substitute) modifier and the path is eaten before git ever sees it — quoting is not a defense, `${C}` is, and only twelve first letters are affected, which is why `docs/...` reads worked for weeks while `src/...` broke. Full fact and fix in [[zsh-eats-a-colon-suffix-after-an-unbraced-var]]. Note what the sequence teaches: the peer correctly refused to infer a cause and stated its claim at the width of its evidence, and that discipline is what made the cause cheap to close afterwards — two commands. **The generalisable half: `git show` with a missing path FAILS OPEN — exit 0, plausible content, no error to catch — and the class is any command whose output silently changes SUBJECT while still answering you.** Grepping a commit diff for an import attributes another file's line to the path you believed you asked for. A probe is immune to this by CONSTRUCTION, not by care: passing `f'{rev}:{path}'` as one argv element from a non-shell caller (Python `subprocess` list form) has nothing to split — though that covers word-splitting only, never a wrong rev. Cheap deliberate control, since the accidental one here was luck: assert a per-file blob read's first line is not `commit [0-9a-f]{40}`.

- **Prefer the command that CANNOT fall back, and assert the subject of what came back.** Measured 2026-08-28: `git show <rev>:<path>` reached git as `git show <rev>` (suffix stripped before argv — not the variable, not quoting, not word-splitting; xtrace-confirmed). The mechanism was closed hours later and it was the SHELL, not git: zsh applies a history modifier to an unbraced expansion, so `$C:src/...` is `$C` plus the `:s` substitute modifier and the path is eaten before argv is built — quoting is no defense, `${C}` is, and only twelve first letters are affected, which is why `docs/...` reads worked throughout while `src/...` broke. See [[zsh-eats-a-colon-suffix-after-an-unbraced-var]].), and `git show <rev>` FAILS OPEN — exit 0, plausible content, no error. It returned a real import line from that commit's diff, belonging to a different file: **true text with a false subject**, which reads as credible evidence rather than as garbage. Read blobs with `git cat-file -p "<rev>:<path>"`, which has no rev-only fallback, and assert the first line is not `^commit [0-9a-f]{40}$`. Generally: a command whose output silently changes SUBJECT still answers you.
